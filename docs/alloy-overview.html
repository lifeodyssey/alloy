Alloy. 一份配置，多个运行时。

概述

什么是 Alloy

Alloy 不是 AI agent，也不是 chat UI。它是 distribution + control layer——你写 packs 声明"我要这些 skill、agent、command、MCP、model 映射"，Alloy 把它们 resolve 出来 materialize 进目标 repo 的运行时目录。

📦 Pack 声明式分发

用 atoms.json 定义原子单位，packs 通过 extends 组合。同一份 atoms 可以 materialize 到不同 runtime（OpenCode → .opencode/、未来 CC → .claude/）。

🪝 12 hooks 深嵌 OpenCode

用 OpenCode 全部 plugin hooks——boot 时注入 config、消息时挂 status、tool 后录 evidence、compaction 时塞 ledger、命令前路由 SDD。

🛠️ 一条命令安装

curl install.sh | bash 自动装 CLI + 写 manifest + 装 shell completion。alloy add/remove/list/upgrade 后续管理。

👥 7 specialist agents

Orchestrator / Explorer / Architect / Builder / Fixer / Reviewer / Tester。SDD pipeline (spec → plan → execute → verify) 把任务路由到合适的 specialist。

📚 概念吸收而非复制

11 first-party fusion skills 把 obra/superpowers、mattpocock/skills、GSD、gstack 等开源项目的概念重写进 Alloy 体系，保留原作者 attribution。

🔄 Sub-agent driven 开发

v0.1.0 本身由 codex sub-agents 实施——5 waves / 11 cards / 14 PRs，coordinator 只做 dispatch + conflict resolution。

关键 hook 代码细看

config hook — boot 时注入默认 + 跑魔法检测 
config: async (config) => {
  if (!config) return
  injectConfigDefaults(config)                  // default_agent ||= 'alloy-orchestrator', mcp baseline
  bootWarnings = await detectMagicWarnings(projectDir)
  bootWarningsChecked = true
  bootWarningsEmitted = false
}

detectMagicWarnings() 检查 3 件事：

  • manifest installedAt 是否比 vendor.lock.json mtime 旧 → "run alloy upgrade"
  • global state.json 的 lastSyncedVendorLock sha 跟当前 vendor.lock 是否不同 → "run alloy install --target global"
  • .opencode/ 存在但 alloy.manifest.json 不存在 → "run alloy install"（v0.1.1 新加）
chat.message hook — 每条消息注入状态 + OMO port 触发 
"chat.message": async (input, output) => {
  await ensureBootWarnings()
  if (bootWarnings.length && !bootWarningsEmitted) {
    output.parts.push(textPart(`## Alloy Startup Warnings\n${bootWarnings.map(w => `- ${w}`).join("\n")}`))
    bootWarningsEmitted = true
  }
  const context = `\n\n## Alloy Workflow Status\n${readStatus(projectDir)}`
  output.parts.push({ type: "text", text: context } as any)

  maybeDelegateTaskRetry({ ...input, message: output.message }, output)  // OMO port
  phaseReminderCount += 1
  maybePhaseReminder(projectDir, output, phaseReminderCount)               // OMO port
}
tool.execute.after hook — 全部 tool 写 evidence ledger 
"tool.execute.after": async (input, output) => {
  maybeRecoverToolJson(output)                                // OMO port: 自动修 malformed JSON
  appendJsonl(projectDir, "evidence", {
    id: randomUUID(),
    taskId: activeTaskId(projectDir),
    kind: input.tool === "bash" ? "command" : "tool",
    source: "opencode-plugin",
    summary: `${input.tool} executed`,
    command: input.args?.command,
    exitCode: output?.metadata?.exitCode,
    paths: [],
    createdAt: new Date().toISOString(),
  })
  if (isRalphLoopToolExecution(input, output))
    recordIteration(projectDir, taskIdFromHookInput(input, projectDir))
}

三件事：JSON 错误修复 + 写 evidence ledger + ralph-loop iteration counter（v0.1.1 加的）。

experimental.chat.messages.transform — filter-available-skills (OMO port) 
"experimental.chat.messages.transform": async (input, output) => {
  if (!output || !Array.isArray(output.messages)) return
  await filterAvailableSkills(projectDir, input, output)
}

filterAvailableSkills() 读 .opencode/alloy.manifest.json，按 manifest.visible.skills 过滤系统消息里的 <available_skills> XML 块。 这是 OMO Slim 的核心机制 port——agent 只看到自己 manifest 允许的 skill，避免"全部 11 个 skill"塞进每条消息。

为什么重要：未过滤时，每个 agent system message 都列全部已安装 skill。filter 后，frontend agent 不会看到 backend skill 描述——节省 token + 减少幻觉调用。
experimental.session.compacting — 让 evidence 跨 compaction 存活 
"experimental.session.compacting": async (_input, output) => {
  if (!output || !Array.isArray(output.context)) return
  const summary = ledgerSummary(projectDir)
  if (summary) output.context.push(summary)
}

OpenCode 触发 compaction 时（session token 接近 cap），把 .alloy/state/*.jsonl 的 ledger summary 塞进保留的 context。 没这个 hook：compaction 后 agent 忘记之前的 evidence/claims，每次重做 verify。

command.execute.before — 拦截 SDD 斜杠命令 
"command.execute.before": async (input, output) => {
  if (!input?.command || !output || !Array.isArray(output.parts)) return
  routeCommand(input, output, projectDir)
}

// routeCommand 内部处理:
//   /add <skill>     → 通过 Bash invoke `alloy add <skill>`
//   /spec /plan /execute /verify /autopilot → 注入 SDD prompt 模板

4 个自定义 tool（给 LLM 调用）

除了 hook，plugin 还注册 4 个 custom tool 在 OpenCode 的 tool registry。LLM 可以像调 bash/read/write 那样调它们。

alloy_evidence

记录工作流 evidence 条目：{taskId, kind, summary, command?} → append 到 evidence.jsonl。用于 verifier 后续核对。

alloy_claim

记录完成 claim：{taskId, text, evidenceIds?} → claims.jsonl。带 evidenceIds 自动标 verified，否则 unverified。

alloy_state

读取压缩 workflow status（当前 task / phase / 待办计数）。供 agent 自我感知当前状态。

alloy_gate

检查 task 是否可关闭：返回 "run alloy gate check --task-id X" 提示 + ralph-loop iteration count (1/5 ... 5/5)。

额外 export：alloy.getIterationCount(taskId)——namespace export 给 ralph-loop skill 直接读 iteration jsonl，避免每次走 file IO。
SDK / CLI

SDK 做了什么，逻辑是什么

Alloy 的"SDK"是 bin/alloy.mjs（CLI 入口 + 全部 resolver/installer 逻辑）+ 3 个 helper module + 1 个 plugin template。 总共约 1900 行 JavaScript/TypeScript 实现了 pack 解析、目录 materialize、manifest 管理、subcommand dispatch、shell completion、vendor 管理。

模块行数职责
bin/alloy.mjs ~1500 主 CLI 入口、参数解析、15 subcommand dispatcher、resolver pipeline (loadAtoms → loadPack → mergePack → resolveConfig)、installer (materialize 到 .opencode/)、doctor、help、completion 生成、SDD command dispatch。
bin/manifest.mjs ~80 .opencode/alloy.manifest.json 读写：{version, installedAt, pack, models, managed, visible, excluded, explicit.added}。Migrate 老 schema (explicit.removed) 自动迁移到 excluded。
bin/state.mjs ~50 ~/.config/alloy/state.json 读写（仅 --target global）：跨项目同步 vendor lock sha 用于 magic detection。
bin/prereq-check.mjs ~50 验证 container-use 等可选依赖：检查 docker/colima/podman 二进制 + container-use 自身。missing 时给安装命令。
templates/opencode/alloy-plugin.ts 674 OpenCode plugin：12 hooks + 4 custom tools + ralph-loop iteration helper。Materialize 到 .opencode/plugins/alloy.ts。
install.sh 207 One-line installer：clone repo → 链接 alloy 到 ~/.local/bin/ → 跑 alloy install --target global → 装 shell completion。set -euo pipefail + 所有变量加引号。
scripts/revendor.mjs ~280 Vendor 维护：从上游 repo clone → diff → 应用 patches → 重算 sha256 → 更新 vendor.lock.json。v0.1.1 修了 shell injection bug (改用 spawnSync argv)。

Resolver 数据流（install 主流程）

// 1. CLI parse
const args = parseArgs(process.argv.slice(2))
// → { command: "install", pack: "frontend", target: "local", models: "github-copilot", ... }

// 2. Load atoms (cached)
const atoms = loadAtoms()   // reads packs/atoms.json once

// 3. Load pack + expand extends
const pack = loadPack("frontend")
// expanded: skills=[alloy-tdd, alloy-brainstorm, ..., frontend-ui-ux, playwright-cli, vercel-react-best-practices]
//           agents=[Orchestrator, Explorer, Architect, Builder, Fixer, Reviewer, Tester]
//           commands=[autopilot, discuss, execute, plan, spec, verify, ...]
//           mcp=[context7, grep_app, exa]
//           modelRoles=[orchestrator, planner, executor, reviewer, verifier, explorer]

// 4. Merge with model assignment + project overrides
const resolved = resolveConfig({
  pack,
  models: loadModels("github-copilot"),       // role → model name
  projectOverrides: loadProjectConfig(cwd),  // .alloy/alloy.project.json
})

// 5. Materialize
installCommand(resolved)
// writes:
//   .opencode/agents/{Orchestrator,Explorer,Architect,Builder,Fixer,Reviewer,Tester}.md
//   .opencode/commands/*.md
//   .opencode/skills/{alloy-*, git-master, humanizer, frontend-ui-ux, ...}/SKILL.md
//   .opencode/plugins/alloy.ts            (from templates/opencode/alloy-plugin.ts)
//   .opencode/opencode.json               (default_agent, mcp, agent→model map, plugin list)
//   .opencode/package.json                (@opencode-ai/plugin + zod pinned versions)
//   .opencode/alloy.manifest.json         (managed + visible + excluded + explicit.added)
//   .alloy/alloy.project.json             (pack + models choice)
//   .alloy/workflow.md + policies/*.md    (workflow docs)
//   .alloy/state/{tasks,claims,evidence,runs,iteration}.jsonl  (empty ledger files)
//   .alloy/projections/{status,current-plan}.md   (placeholder, plugin updates)
//   .safety-net.json                      (5 git no-verify rules at project root)

// 6. Global tier extra (--target global)
if (resolved.target === "global") {
  writeState("~/.config/alloy/state.json", {
    version, installedAt, pack, managed,
    lastSyncedVendorLock: sha256(vendor.lock.json),
  })
}

.alloy/state/*.jsonl — 5 个 append-only ledger

JSONL 格式（每行一个 JSON object），source of truth。.alloy/projections/*.md 是从 jsonl 生成的人读视图。

  • tasks.jsonl — Architect 写入的 task plan
  • evidence.jsonl — tool execution outputs，由 tool.execute.after hook 自动 + LLM 调 alloy_evidence tool 写
  • claims.jsonl — agent 声明的完成 claim，带 verified/unverified 状态
  • runs.jsonl — OpenCode session events + permission asks audit trail
  • iteration.jsonl — ralph-loop 计数（v0.1.1 加），记录 5-iter cap 用
Agents

7 个 v3 specialist 与 workflow

v0.1.0 Card 4 把旧的 6 个 alloy-* agents（小写连字符）替换为 7 个 specialist（PascalCase）。 每个有明确职责边界，由 Orchestrator 根据任务类型 dispatch。

🧭 Orchestrator

Router。识别请求类型，dispatch 给 specialist。不直接干活，专注 intake + coordination + final synthesis。

🔍 Explorer

Read-only 代码发现。grep/glob/读文件，回答"X 在哪定义/被谁调用"，给路径 + 关键 symbol + uncertainty。

🏛️ Architect

写 ## Spec + ## Plan、source coverage 审计、design risk 评估。不写实现。

🔨 Builder

新代码 + 行为改动。强制走 alloy-tdd：failing test 先、最小实现、refactor。bounded scope。

🔧 Fixer

bug / regression / failing check。强制走 alloy-debug：reproduce → root cause → regression test → fix → verify。

👁️ Reviewer

独立 review。Critical/Important/Minor 三级 severity。不修自己发现的 bug（避免利益冲突）。Critical 阻塞完成。

🧪 Tester

测试设计 + 独立验证 + edge case 生成。强制走 alloy-verify 才能 claim "complete/passing/ready"。

Agent MD 文档结构

每个 agent 是一个 markdown 文件，agents/<Name>.md。frontmatter + body 两段。

Frontmatter 字段

字段类型说明
descriptionstring一句话描述 agent 用途。Orchestrator 加载时基于此分发。
modeprimary | subagentprimary = 用户直接对话；subagent = 只被其他 agent 通过 task tool 调用。
permissionobject细粒度权限：read/grep/glob/bash/task/skill。每项 allow|ask|deny 或 bash 命令 pattern map。

典型 body sections

  • Responsibility — 一段说明这个 agent 干什么、不干什么
  • Permissions — body 重复 frontmatter 权限的人读解释
  • Skill Guidance — 什么时候 invoke 什么 skill
  • Intake Rules（Orchestrator 特有）— 怎么 normalize work item metadata
  • Routing Matrix（Orchestrator 特有）— 决策树
  • Phase Discipline — Plan / Execute / Verify 三阶段约束
  • Global Rules — 硬规则（git no-verify 禁用、explicit file staging 等）
  • Example Flow — 1-3 个 worked example
  • Output Contract — 返回结果的固定格式要求

# Alloy Orchestrator

You are the v3 Alloy router. Your job is to understand the user's request, choose the
smallest safe workflow, and dispatch task-typed specialists without turning every
request into process theater.

## Responsibility

Route work across the six specialists:

- `Explorer` for read-only source discovery and compact summaries.
- `Architect` for specs, `## Plan` sections, source coverage audits, and design risk.
- `Builder` for new code and behavior changes via `alloy-tdd`.
- `Fixer` for bugs, regressions, and failing checks via `alloy-debug`.
- `Reviewer` for independent code review with Critical / Important / Minor severity.
- `Tester` for test design, test execution, verification evidence, and completion checks.

You do not do every job yourself. Keep the main session focused on routing, intake,
coordination, and final synthesis.

## Skill Guidance

Invoke relevant skills before acting:

- Use `alloy-using` at session start when available.
- Use `alloy-discuss` for large or ambiguous product requests.
- Use `alloy-brainstorm` when the design space is still fluid.
- Use `alloy-plan` when a spec needs an implementation plan.
- Use `alloy-execute` when executing a written plan.
- Use `alloy-tdd` for code changes.
- Use `alloy-debug` for bugs, regressions, and failing tests.
- Use `alloy-verify` before completion claims.

## Routing Matrix

### Read-Only Codebase Question
Dispatch `Explorer` with a narrow question and expected output shape.

### Product Or Architecture Design
Use `alloy-discuss` or `alloy-brainstorm`, then dispatch `Architect`.

### New Implementation
Tiny → `Builder` directly. Multi-file → `Architect` writes Plan first.

### Bug Or Failing Test
Route to `Fixer`. Require reproduction, root cause, regression test.

### Review / Verification
Route to `Reviewer` (independent) then `Tester` (verify).

## Phase Discipline

Alloy v3 has three central phases:
1. Plan: clarify scope, inspect code, write spec and `## Plan`.
2. Execute: build or fix one bounded task at a time.
3. Verify: test, review, inspect artifacts, and record evidence.

## Global Rules

- Never use `--no-verify` or `-n` with git.
- Never use `git add -A`, `git add .`, or `git add --all`.
- Never force-push except `--force-with-lease`, and only with user approval.
- Before deleting 5+ lines or changing public interface, search references.

## Output Contract

When coordinating specialists, return:
- route chosen and why
- agents used
- files changed or inspected
- verification evidence
- unresolved blockers or risks

其他 6 个 agent MD 在 github.com/lifeodyssey/alloy/tree/main/agents。 结构类似但更短——Orchestrator 是最长的（160 行），specialist 一般 50-100 行。

   ~/.config/opencode/
